## 0. 产品目标与闭环

**产品目标：** 帮助拥有 Apple Watch 的普通运动者理解身体变化、合理安排运动，并看见有证据支持的个人进步。首个验证场景为日常骑行，之后扩展到步行、跑步等大众运动。

**核心闭环：**

```text
理解身体 → 制定目标 → 完成运动 → 评估表现 → 调整下一次训练
```

| 闭环环节 | 对应能力 | 版本 |
|---|---|---|
| 理解身体 | 个人基线（静息心率 / HRV）、睡眠分析、数据充足性 | v0.2 已实现（待真机验收） |
| 制定目标 | 个人运动目标、简单训练计划 | v0.3 / v0.4 |
| 完成运动 | Watch 运动采集与镜像（v0.2 已实现）；**读取 HealthKit 中任意来源的运动记录** | v0.2 / v0.3 |
| 评估表现 | 运动后反馈、历史进步分析、主观疲劳记录 | v0.3 |
| 调整下一次训练 | 可解释的训练建议与计划执行反馈 | v0.4 |

**产品验证成功标准（摘自产品战略）：** 用户能理解至少一个重要变化、更有把握地完成一次合适训练、在数周内发现有证据支持的进步，并因此愿意持续使用。功能数量不是成功指标。

**非目标：** 医学诊断；由 HRV / 静息心率 / 睡眠直接推断疾病、过劳或“恢复程度”；0～100 恢复分或“身体电量”等综合评分；用缺失数据生成分数或判断；无传感器的踏频 / 功率；未经明确授权的健康数据上传；强迫用户改用 WatchPulse 记录运动。

### 0.1 路线图设计规则

1. **核心闭环优先。** v0.3–v0.5 只做闭环所需能力；与闭环无直接关系的功能一律进入“候选增强”（第 2 节），由产品验证证据决定是否拉入。
2. **数据来源中立。** 评估、目标、计划一律建立在 HealthKit 的运动记录之上（见 1.1）。WatchPulse 自己的 Watch 运动、镜像、骑行码表是可选的采集通道，不是闭环的前置条件。
3. **确定性计算在先，AI 在后。** 所有数值、对比、规则由可测试的确定性代码产生；AI（可选路线，见 1.0 / 1.6）只负责解释，不替代计算和安全判断。
4. **样本不足就说不足。** 每条结论必须带依据（对比对象、样本数、时间窗）；达不到门槛显示“积累中”，不输出分数或判断。
5. **用户决定权。** 目标、训练建议是否采纳、健康数据的使用范围都由用户决定；建议可忽略、可修改，被忽略后不反复打扰。

### 1.0 两条路线（AI 与 v1.0 解耦）

```text
核心产品路线（决定 v1.0 能否发布）：
  v0.3 目标与反馈 → v0.4 训练计划 → v0.5 周报与日常体验 → v1.0 稳定发布

可选 AI 路线（独立排期，不是 v1.0 的前置条件）：
  AI-1 基础评估 → AI-2 解释 → AI-3 问答与建议说明
```

* **v1.0 的发布条件只取决于核心路线**：关闭 / 不存在 AI 时，v0.3–v0.5 的全部功能必须完整可用，v1.0 可以在没有任何 AI 能力的情况下发布。
* **AI 路线的并入时机由证据决定**：基础统计与规则经真实使用验证（产品战略阶段一 / 二 / 三）后，AI-1 起才可启动；AI-x 完成评审后可并入 v0.5 之后的任一小版本或 v1.x，也可以推迟或取消。AI 不占用 v1.0 的版本号与验收名额。
* AI 与核心路线的唯一接口是“确定性摘要层”（见 1.6）；核心路线不为 AI 预留未验证的数据出口，也不因 AI 改变已有的计算与文案。
* 保留全部隐私原则：本地优先、默认关闭、云端处理需明确授权；本次修订**没有**增加任何云端健康数据处理。

**优先级：** P0：错误 / 丢数据、安全状态、核心闭环；P1：必备界面与可理解的信息；P2：锦上添花。一个版本内保持 P0 少且验收可判定。

### 1.1 运动数据来源：优先复用 HealthKit（v0.3 起适用于全部分析）

目标：用户可以继续用 Apple 原生「体能训练」或其他 App 记录运动，WatchPulse 直接读取「健康」中的运动记录完成目标跟踪、运动后反馈与进步分析，不强迫通过 WatchPulse 开始运动。

- **读取范围：** 通过 HealthKit 读取任意来源的 `HKWorkout`（含 Apple 原生「体能训练」、WatchPulse、第三方 App），及其关联的心率、距离、能量等样本。iPhone 运动历史已按此读取并映射类型（见 DEVICE_VALIDATION.md 4.3，**该项尚未真机验证**）。
- **来源标注：** 每条记录显示来源；分析口径中明确标出使用了哪些来源。
- **去重：** 同一次运动被多个来源重复记录时，须有确定的、保守的重复检测规则（详见 1.3.1-A）：**绝不**仅凭“时间重叠 + 类型相同”判定重复；只读取、不删除也不修改 HealthKit 中的任何运动；结果分为确认重复 / 疑似重复 / 独立运动，疑似重复不得静默丢弃，并有单测。
- **数据完整度：** 缺少距离、心率或起止时间的记录，只参与它具备数据的那部分分析；缺失项显示 `--`，不补 0。
- **能力降级：** 路线、实时速度、区间提醒等依赖 WatchPulse 采集的细节指标只在有这些数据时出现；原生记录没有的指标不伪造。
- **可比性：** 进步分析只比较“可比”的运动（类型、室内 / 室外、时长或距离区间相近，见 v0.3），不同来源的口径差异需在文案中说明。
- **真机验证：** 在 DEVICE_VALIDATION.md 中新增“原生体能训练记录”相关验证项，真机核对前不标通过。

#### 1.2.1 v0.2 验收分级：Release Blocking 与非阻断探索

DEVICE_VALIDATION.md 中每个验证项都有“分级”（RB / EX），汇总见该文件“验收分级”一节。

* **Release Blocking（RB）：** 数据正确性（与「健康」App 一致）、运动保存、权限处理、核心镜像稳定性（开始 / 镜像 / 控制 / 断线恢复 / 结束送达）、骑行核心口径（速度、均速、区间）。**任何一项 ❌ 或长期 ⬜ 都阻止 v0.2 签收，不得忽略。** 失败项必须修复并复测。
* **非阻断探索（EX）：** 暂时难以复现的特殊场景（隧道、锁屏长时间、结束瞬间断开）、需长期使用才能观察的体验（电量、2 小时以上运动）、增强类验证（VoiceOver、动态字体、版本互相兼容）。结果记录在案、发现缺陷进入待办，**不阻塞 v0.2 签收**；但若探索中发现数据错误或丢数据，立即升级为 RB。
* **与 v0.3 的并行规则（1.2.1-P）：** 允许在 RB 项未全部通过时，并行推进 v0.3 的**纯逻辑**开发（`WatchPulseShared` / `WatchPulseCore` 中不改变既有行为的新增类型与测试）。并行期间：①不得修改已验证项涉及的行为（HealthKit 读取结果、Workout Mirroring、运动保存、Demo 模式）；对 `HealthKitWorkoutMapping` 等边缘代码只做**只增字段**的改动；②不向稳定分支合并；v0.3 任何涉及界面或 HealthKit 边缘的改动，须在对应 RB 项通过后才可合入稳定分支；③RB 项复测发现的缺陷优先于 v0.3 工作。

### 1.3 v0.3 目标与反馈（制定目标 → 完成运动 → 评估表现）

**目标：** 用户设定自己的运动目标，每次运动后看到基于自己历史的反馈，并能判断是否真的在进步。

| 任务 | 优先级 | 内容 |
|---|---|---|
| **T1 运动数据层** | P0 | 在现有 HealthKit 运动历史上建立统一的“运动分析记录”（`WorkoutAnalysisRecord`）：来源（含 bundle / 设备 / 外部标识）、类型、室内外、时长、距离、心率、区间分布（带口径标注）、数据完整度、心率归属可信度、重复状态与**分析资格**；实现 1.3.1 的保守去重、心率可信度与区间口径规则。复用 `HealthKitWorkoutHistoryService`、`WorkoutRecord`、`HeartRateAttribution`，不重写查询层。 |
| **T2 个人运动目标** | P0 | 本地存储的目标：每周运动次数 / 总时长、骑行每周距离（可选）。进度完全由 HealthKit 运动记录计算，用户可编辑、暂停、删除目标；不预设“应该达到”的数值，不自动调高。 |
| **T3 运动后反馈** | P0 | 对任意来源的一次运动，给出确定性、可解释的摘要：与自己最近同类运动比较时长、距离、均速、平均心率、区间分布；每条结论显示对比对象与样本数；同类样本不足则不下判断，只展示本次数据。 |
| **T4 历史进步分析** | P0 | 只在“分析资格”为可比较的运动之间（同类型、同室内外、同来源与同设备族、距离 / 时长相近、心率区间口径一致）展示滚动对比与趋势（如 4 周对前 4 周）；“相同心率下的速度 / 配速”等指标只在可比样本充足时展示；显示证据（样本数、时间窗、来源）；不足显示“积累中”。避免把天气、路线、设备差异造成的波动写成进步或退步。 |
| **T5 主观疲劳记录** | P1 | 运动后可选记录主观强度（如 1–10 自觉用力程度）及当天身体感受，本地存储，关联到稳定的运动记录标识；可跳过、可修改、可删除，不强制。与客观数据并列展示，不合成分数。存储、孤儿记录与换机规则见 1.3.2（**契约已在 T1 阶段定义，UI 与持久化实现留给 T5**）。是否同步写入 HealthKit（iOS 18 起提供运动强度类数据类型）作为待评估项，默认仅本地。 |
| **T6 与“理解身体”衔接** | P1 | 在目标 / 反馈页并列展示近期基线变化与睡眠（仅描述，不做因果与诊断），帮助用户把身体状态与运动安排放在一起看。 |

#### 1.3.1 数据可信度规则（T1 起，所有分析必须遵守）

**A. 运动记录去重（P0）**

原则：HealthKit 原始记录一律保留，WatchPulse 只在分析层做“分组与标注”，不删除、不修改、不回写。“时间重叠 + 类型相同”**不足以**判定重复（连续两段运动、短步行嵌在长骑行里、多来源各自独立记录同一时段的不同活动都会命中该条件）。检测按下列优先级确定性执行，结果与输入顺序无关：

| 判定 | 条件（全部满足） | 统计处理 |
|---|---|---|
| **确认重复** | 活动类型相同，且满足其一：① 同一 `HKWorkout` UUID；② 两条记录带有相同的外部标识（`HKMetadataKeyExternalUUID` 或 `HKMetadataKeySyncIdentifier`，非空）；③ **同一物理设备**（设备名 + 型号 + 硬件版本一致）、**不同来源**、开始与结束时间各相差 ≤ 2 秒、室内外不冲突、距离（双方都有时）相差 ≤ 2% | 合并为一条“主记录”（按完整度 → Apple 原生来源 → 较早开始 → UUID 排序选取，确定性），其余记录作为“被合并来源”保留在主记录上，界面可追溯 |
| **疑似重复** | 活动类型相同、来源**不同**、开始相差 ≤ 120 秒、结束相差 ≤ 120 秒、时间交集 ÷ 并集 ≥ 80%（三者同时满足，避免短运动嵌在长运动中被误判）、室内外不冲突、距离（双方都有时）相差 ≤ 10%，但不满足“确认重复” | **两条都显示并标注“疑似重复”**；统计总量时默认**只计一次**（取排序最前者），并在结果中明确返回“含 N 条疑似重复，已按一次计入”；两条都**不**进入进步比较（证据不确定）；用户确认后的取舍结果属于后续任务（预留接口，不在 T1 实现） |
| **独立运动** | 其他一切：类型不同（如骑行 + 步行）、同一来源的两条记录（除非外部标识相同）、重叠比例低（短运动嵌在长运动中）、距离矛盾、室内外冲突 | 各自独立计入 |

* 疑似重复**不传递**：判定只在直接两两之间成立，不会因 A≈B、B≈C 把 A 与 C 连成一组。
* 来源比较使用 `bundleIdentifier`，缺失时退回来源名称；两条记录来源信息都缺失时只能判“独立”或“疑似”，不能判“确认”（②③ 需要可靠标识）。
* 测试必须覆盖：重叠但并非重复、跨来源重复、同源连续运动、类型不同、距离矛盾、短运动嵌入长运动、输入顺序无关、时区 / 夏令时（判定只用绝对时间）。

**B. 心率区间口径（P0）**

仓库里存在两种口径，必须在模型与文案中显式区分，不得混用：

| 口径 | 类型 | 参照 | 用途 | 可比较 |
|---|---|---|---|---|
| **个人训练区间** | `TrainingZone` + `HeartRateZoneSettings`（Z1–Z5，用户输入最大心率或下限） | 用户确认的个人配置 | Watch 实时提醒、iPhone 码表区间条、**历史进步分析** | 仅当两次分析使用**相同**的区间配置（最大心率与各下限一致）才可比较 |
| **本次相对区间** | `HeartRateZone`（热身…极限） | 本次运动自身的最高心率 | 运动详情的“本次强度分布”展示（保持现状，兼容） | **不可跨运动比较**（参照随每次运动变化） |

* 进步分析与目标进度只使用**个人训练区间**；未配置时显示“未设置个人心率区间”，进步分析中不使用相对区间，**不用 220−年龄 等推算值冒充最大心率**。
* 每个区间分布结果都带 `HeartRateZoneBasis`（口径种类、最大心率来源 `用户输入 / 本次观测最高值`、各下限、配置指纹），保存或展示时一并标注；用户修改区间配置后，历史分析用**当前配置对原始样本重新计算**，不拿旧配置结果与新配置结果混比。
* 本次相对区间的“最大心率”是**观测值**，文案须标为“本次最高心率”，不得称为“最大心率”。

**C. 心率数据归属可信度（P0）**

复用现有 `HeartRateAttribution`，并加入有效采样覆盖率与异常处理，得到每次运动的**心率可用级别**（由低到高）：

| 级别 | 条件 | 允许的用途 |
|---|---|---|
| 无数据 | 没有样本 / 有效样本为 0 | 不展示心率结论 |
| 仅可展示 | 归属为 `timeRangeAllSources`（仅按时间匹配的全来源样本，可能混入其他设备）；或覆盖率 < 60%；或有效样本 < 12；或异常样本比例 > 10% | 展示曲线与数值并标注原因；**不进入汇总统计，不用于任何表现结论** |
| 可汇总 | 归属为 `sameDevice`（同设备同时间段，需标注），或 `workoutAssociated` 但覆盖率在 60%–80% | 可计入平均心率等汇总，并附带说明；**不用于跨运动表现比较** |
| 可比较 | 归属为 `workoutAssociated`（与运动直接关联），覆盖率 ≥ 80%，有效样本 ≥ 12，异常比例 ≤ 5% | 可用于“相同心率下的速度 / 配速”“区间分布对比”等表现结论 |

* **覆盖率** = 样本间隔 ≤ 60 秒的累计时长 ÷ 运动时长（与现有区间时长的缺测口径一致）；超过 60 秒的间隔视为缺测，不补插。
* **异常样本：** 非有限值、超出 30–230 次/分、时间戳不在运动窗口内（容差 5 秒）、与上一个样本时间戳完全相同的重复样本；异常样本被排除并计数，不静默修正。
* **“可展示”不等于“可比较”。** 归属可信度不够时，界面仍可展示曲线，但相关结论一律降级。

**D. 分析资格（Eligibility）**

每条分析记录同时给出三层资格及原因，供 T2–T4 直接使用，避免各处自行判断：

1. **可展示：** 时间区间合法（结束 ≥ 开始，时长 > 0）即可展示；其余缺失字段显示 `--`，不补 0。
2. **可统计（次数 / 时长 / 距离合计）：** 可展示 + 不是被疑似重复排除的那一条 + 时间合法。
3. **可进步比较：** 可统计 + 不处于疑似重复 + 室内外已知。**按指标降级**（`WorkoutMetric`）：时长始终可比；距离 / 均速只在有距离时；平均心率、相同心率下的速度只在心率可用级别为“可比较”时；个人区间分布还需用户确认的区间配置。同来源、同设备族在**两次运动之间**判定（`WorkoutComparability`）。
4. 演示数据始终带 `simulated` 标记，不与真实数据混合统计。

**时区与夏令时：** 所有时间判定使用绝对时刻；按“天 / 周”聚合时由调用方传入 `Calendar`（含时区），记录按**开始时刻**归属当地日历日；夏令时当天（23 / 25 小时）不重复、不丢失，时长始终使用 `duration`（秒），不用墙上时间相减。

**E. 可比较性规则（`WorkoutComparability`）**

两次运动要在进步分析中比较，需同时满足：同活动类型；室内外均已知且相同；**同来源**（bundle / 名称）；**同设备族**（硬件 / 型号相同；一方已知另一方未知则不可比；双方都未记录设备且来源相同时可比，但附“未记录设备，无法发现设备更换”说明）；双方都有距离时距离比值、否则时长比值在 1/1.5–1.5 内；个人区间分布只在区间配置完全一致时参与（其余指标不受影响）。任何一条不满足都返回具体原因（来源变化、设备变化、型号未知等），界面据此说明“因设备变化，该次运动不参与对比”，而不是悄悄纳入。

#### 1.3.2 主观疲劳记录的存储契约（T5 前置，T1 只定义契约）

| 项 | 规则 |
|---|---|
| 存储位置 | 仅本机（App 的 Application Support 目录内 JSON / 本地数据库），**不引入云端同步、账号或第三方 SDK**；不写入 HealthKit（待评估项另议） |
| 关联键 | `WorkoutKey`：HealthKit 运动 UUID（主键）+ 指纹（开始时刻、活动类型、时长、来源标识、外部标识），指纹用于 UUID 变化时重新关联 |
| 内容 | 自觉用力程度 1–10（可空）+ 身体感受标签（可多选，可空）+ 创建 / 修改时间 + 契约版本号；两项都空则不保存；可跳过 |
| 编辑 | 同一运动至多一条记录；可修改（更新修改时间）、可删除（物理删除，不留墓碑）；与客观数据并列展示，不合成分数 |
| 运动记录消失 | 用户在「健康」中删除运动后：记录标记为“未关联”（保留，不参与任何分析与展示），先尝试用指纹**唯一**匹配新的运动 UUID 并自动重新关联；不唯一或无匹配则保持未关联；**不自动删除**用户填写的内容，由用户在设置中手动清理 |
| 重装 | 删除 App 会删除本地数据，**不可恢复**；若用户启用了系统设备备份（iCloud / 本机备份），App 数据随系统备份一起恢复，WatchPulse 自身不做同步 |
| 换机 | 通过系统备份还原或“设备迁移”时随 App 数据迁移；全新安装（不还原）不会有历史记录。HealthKit 运动 UUID 在 iCloud「健康」同步 / 备份还原后**通常保持不变，但不作保证**，因此依赖指纹重新关联，关联失败时保持未关联 |
| 隐私 | 内容不上传；R5 的本地导出（v0.5）是用户主动操作 |
| 文案 | 必须告知用户“仅保存在本机，删除 App 或换机且未恢复备份会丢失” |

**验收：** 新逻辑 Linux 单测（保守去重、完整度降级、心率归属与覆盖率、区间口径、可比性筛选、样本门槛、统计与目标进度跨时区 / DST）；Demo 模式 UI 测试；在包含 Apple 原生「体能训练」记录的真机上核对列表、反馈与进度；文案不含诊断性结论。
**个人验证：** v0.2 真机验收完成后，立即开始产品战略中的“阶段一”（连续 4 周、至少 8 次运动），记录使用障碍、数据问题和因反馈而改变的训练行为。

### 1.4 v0.4 训练计划（调整下一次训练）

**目标：** 在目标与历史反馈的基础上，给出可解释的下一次训练建议，并在执行后给出反馈。

| 任务 | 优先级 | 内容 |
|---|---|---|
| **PL1 简单训练计划** | P0 | 围绕 v0.3 目标生成 / 手动编辑每周计划：每次训练的类型、预计时长或距离、目标强度（可用个人心率区间 Z1–Z5 或主观强度表达）。计划模板简单（如轻松 / 节奏 / 长距离），用户可全部修改；不追求专业周期化。 |
| **PL2 下一次训练建议** | P0 | 确定性规则，输入为：目标进度、近期训练量与间隔、主观疲劳记录；基线与睡眠变化只作为“参考信息”展示，**不单独触发降低强度的断言**。每条建议附带理由与依据，并给出“采纳 / 修改 / 忽略”。 |
| **PL3 计划执行反馈** | P0 | 用 HealthKit 中的运动记录（任意来源）自动匹配计划，比较完成度与强度（时长、距离、区间分布）；匹配规则透明，匹配错误可手动更正；不要求通过 WatchPulse 开始运动。 |
| **PL4 调整反馈** | P1 | 计划连续未完成、主观疲劳持续偏高或明显超额时，给出保守、可解释的调整建议（如减量 / 保持 / 延后），始终可忽略；被忽略的建议不重复打扰。 |
| **PL5 Watch 端支持** | P2 | 在 Watch 上查看当日计划与目标强度，复用 v0.2 的心率区间提醒；仅在能直接服务训练执行时做，不作前置依赖。 |

**安全边界：** 建议用于一般健身与生活方式参考；不提供医学诊断；出现用户标记的身体不适时，建议默认为“休息 / 咨询专业人士”类提示，不推高强度；不生成医疗化的“恢复”结论。
**验收：** 规则全部有确定性单测（含边界与样本不足）；每条建议可追溯到输入数据；采纳 / 忽略路径的 UI 测试；真机以 2 周以上的真实使用验证建议的合理性。
**外部验证：** v0.4 可用后启动“阶段二”（5～8 位目标用户、约两周），观察独立完成流程的能力、自发使用频率、实际价值和放弃原因。

### 1.5 v0.5 周报、长期趋势与日常体验

| **R1 健康运动周报** | P0 | App 内周报：目标完成情况、计划执行、运动量与强度分布、静息心率 / HRV / 睡眠变化（描述性）、主观疲劳概览、本周值得注意的 1～3 件事（每件带依据）。先明确“本周”口径（上一个完整自然周或滚动 7 个完整日，不混用）；样本不足的部分不计算百分比或 0 值。 |

### 1.6 可选 AI 路线（AI-1 → AI-2 → AI-3，与 v1.0 解耦）

**前提：** 基础统计、解释逻辑与训练建议规则已在真实使用中验证后才启动；若验证显示价值有限，可推迟或取消。**AI 是体验增强，不是产品价值本身，不是 v1.0 的前置条件，也不是现阶段的开发重点。** AI 路线没有独立版本号；每个阶段通过评审后，可并入 v0.5 之后的任一小版本或 v1.x。

| 阶段 | 内容 | 并入门槛 |
|---|---|---|
| **AI-1 基础评估** | 定义“AI 输入摘要”：只由确定性计算产出的最小结构化摘要（指标、对比、样本数、来源、数据可信度等级），不含原始样本、位置轨迹或可识别信息；设计隐私设置页与授权流程；建立评估集（事实一致性、有无诊断性措辞、数据不足时是否拒答）；评估端侧模型（如系统提供的端侧能力，需满足系统版本与设备要求）与云端方案的取舍。**本阶段不接入任何云端服务。** | 隐私与授权设计评审通过；评估集建立 |
| **AI-2 解释** | 周报摘要与“这次变化意味着什么”的自然语言解释；默认关闭，用户主动开启；输出中的数值必须来自输入摘要并可校验；每段文字可展开查看依据。 | 事实一致性与“无诊断”评估达标；关闭 AI 时全部功能不受影响 |
| **AI-3 问答与建议说明** | 针对个人数据的问题解答与对既有建议的解释；AI 不直接修改计划，不绕过确定性规则与用户确认；对医疗 / 诊断类问题使用固定的安全回复并建议咨询专业人士。 | 护栏与降级验证；阶段三决策确认投入价值 |

AI 摘要层只接受“分析资格”达到 **可用于统计 / 可比较** 的数据（见 1.3.1）；仅可展示的数据不得进入 AI 摘要的强结论字段。

**数据隐私与授权边界（硬性要求）：**

1. 默认关闭，且关闭时全部非 AI 功能完整可用；
2. 任何云端处理都需用户明确授权，授权说明包括：发送什么内容、发给谁、用途、保留时长、如何撤销；
3. 发送前可预览内容；授权可随时撤销，撤销后停止发送，并提供删除已发送数据的途径（以服务条款允许范围为准）；
4. 数据最小化：只发送确定性摘要，不发送原始心率 / 睡眠样本、位置轨迹、姓名或联系方式；
5. 优先端侧处理；云端方案须说明数据是否用于模型训练，并以不用于训练为前提；
6. AI 不替代确定性计算与安全判断；输出需带“一般健身参考，非医疗建议”的边界说明；
7. 输入摘要与输出的关键数值需可审计（本地保留记录，可查看、可清除）；
8. 任一环节出错或不可用，回退到确定性文案，不阻断主流程。

### A.3 两条并行主线的范围

#### A.3.1 Cycling Track（C）

**C1 / P0：指标契约**。在现有 `WorkoutMetricsSnapshot` 增加 `speedMetersPerSecond?`、`speedSampleDate?`、`speedSource?`、`speedQuality?`（或等价可选字段），考虑旧/新消息的 `Codable` 兼容性和既有 `WorkoutMirroringCodec.currentVersion`。原则：旧格式仍应可解码（若破坏兼容，则明确升级版本和降级策略）。增加离线 deterministic tests。

**C2 / P0：GPS 测速服务**。使用 Core Location 的 `CLLocation.speed`；单位为 m/s，显示乘以 3.6 转 km/h。仅室外骑行启用；检验时间戳、有效性（例如 `speed < 0` 为无效）、定位精度和速度精度；过滤跳点，采用少量近期数据平滑，位置过期标记 unavailable。所用阈值集中为配置参数，需真机校准。暂停时不累计移动时间；Watch 作为主计时/运动状态源；不新增另一套 workout session。GPS 权限拒绝时保留心率/时长/已有距离。

**C3 / P0：平均速度与时间定义**。优先以运动记录距离和有效运动时长计算均速，显示“运动均速”；移动均速可放 v0.3，但不可混用口径。处理 0 秒、缺失距离、暂停/恢复、运动类型切换及断线恢复。

**C4 / P0：个人心率区间**。支持用户手动输入最大心率或者直接设置区间边界；不得未经说明直接以 220-年龄等公式标成真实最大心率。Z1–Z5 定义清晰、边界不重叠、可重置与本地存储。目标区间在设置完成后才能启用提醒。区间解释为训练参考，不是医学诊断。

**C5 / P0：Watch 震动提醒**。Watch 本地以连续多个有效心率样本或 8～10 秒持续越界触发；例如最短冷却 60 秒、回到区间需滞后区间阈值（hysteresis）才能再次触发；暂停/停止/样本过期不得提醒；默认关闭，UI 可关闭。必须验证 Haptic 对 HR 采样及电量影响。系统允许 active workout 期间发 haptic，但不应频繁调用。

**C6 / P1：骑行 UI**。Watch 和 iPhone 分别显示速度、均速、时间、心率、区间、来源/数据状态。UI 必须支持 0 / nil / stale / GPS denied / disconnect / paused / saving / saved / failed；Demo 随机/确定性 GPS 轨迹可通过依赖注入产生，不写真实 HealthKit。

**C7 / P1：骑行回归测试和设备清单**。确保旧的 workout saving/mirroring 不回退；模拟 GPS 0/负值/时间倒退/高噪声/断线/后台/恢复；新增 `docs/DEVICE_VALIDATION.md` 项，至少完成一次 20+ 分钟真实骑行的速度、距离、心率、暂停与电量观察。

#### A.3.2 Health Track（H）

**H1 / P0：日趋势统计与质量标签**。复用已有 `HealthDataService` / `HealthKitHealthDataService` / `MetricTrendViewModel`，不要重写查询层。构造“每天一个数据点”的明确模型，按本地时区/Calendar 处理日期、DST；标记 missing、notAuthorizedOrUnavailable、sourceFallback 和 freshness。读权限不可通过空查询证明已拒绝。

**H2 / P0：个人基线**。初版用最近完整 7 天为观察期、此前连续 28 天为参考窗口；静息心率与 HRV 分开统计，以有效日值的中位数（median）为基线。参考窗口至少 14 有效日，观察期至少 4 有效日，否则报告“数据不足”；展示两组中位数及差值，不产生“生病/过劳/恢复到位”等诊断结论，不合成 0～100 恢复分。所有算法时间窗、样本数和理由可解释、可测试。

**H3 / P0：睡眠基础分析**。复用已修复的 `SleepAggregator` 和 `primarySourceName`，展示睡眠/清醒/REM/核心/深睡，只有 inBed 数据时必须明确标注“只有卧床记录，无法推断实际睡着时长”。睡眠起止跨午夜按夜归属、DST、来源冲突、被拆分的睡眠段需测试。不要把 REM/深睡比例描述为医学诊断。

**H4 / P1：分析页面 UI**。新增 `WatchPulse/Features/Insights/` 与 ViewModel。默认展示最近趋势、自己基线差异、数据样本数、最近同步时间、数据来源和一条谨慎的文案；卡片可进入原有趋势页。无权限/无数据/不足/部分失败各自有 Preview、UI 测试。

**H5 / P1：模型缓存**。优先计算式与现有本地模型；如果 28～35 天查询导致页面慢，可加本地轻量缓存、并且明确过期时刷新。禁止在未经批准情况下引入云端、账户系统或第三方遥测 SDK。

**H6 / v0.3：健康周报**。明确“本周”采用上一个完整自然周或滚动过去 7 个完整日，不能混用。包括总骑行次数与距离、静息心率变化、HRV 变化、平均睡眠和有效样本天数。源数据不足时不计算虚假的百分比或 0 值。初期 App 内显示即可，系统通知与 Widget 放后续。
